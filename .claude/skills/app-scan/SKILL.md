# App Store / Google Play 工具榜扫描分析

分析 `data/{今天日期 YYYY-MM-DD}/{platform}/apps.json` 中的非国区工具榜数据
(platform=ios 或 play),生成中文分析报告到 `reports/{日期}-工具榜分析-{platform}.md`。

## 参数解析

从用户输入解析:平台 `ios`(默认)/ `play`;模式 `light` / `standard`(默认)/ `deep`;`--refresh`。

## 流程

1. **取数**:若 `data/{日期}/{platform}/apps.json` 不存在或带 `--refresh`,
   先运行 `python3 -m fetch.charts --platform {platform} [--refresh]`(工作目录为项目根)。
   脚本失败(退出码非 0)→ 向用户报告错误并停止。
   play 平台依赖:需 node + 项目根已 `npm install`,且运行时需代理可访问 play.google.com。
2. **读数据**:读 `apps.json`(已按最佳排名排序)与 `meta.json`。
   `meta.json` 的 `skipped` 非空 → 报告"本期总览"须注明缺失的区域/榜单。
3. **类型分布**(所有模式):把 app 归入细分赛道(如 清理加速 / 网络VPN /
   文件管理 / 格式转换 / 效率工具 / 安全隐私 / 输入法 / 小组件壁纸 /
   扫描识别 / 测试与其他)。依据 `details.genres`、名称与描述关键词。
   统计各赛道数量与占比,指出跨区域共性赛道与区域特色赛道。
4. **可行性过滤**(所有模式):按「独立开发者可行性清单」(见下)把每个
   细分赛道标记为 可实现 / 不可实现——政务、运营商等多语言长尾靠
   语义判断,不做关键词硬匹配。不可实现赛道的 app 不进入重点分析、
   评论抓取与智能推荐;完整榜单表格仍保留全量。
5. **分层分析**(对象=可行池,按最佳名次排序):
   - `light`:无逐个详析,全部表格化。
   - `standard`:取可行池前 120 个逐个详析,其余表格化。
   - `deep`:取可行池前 30 个逐个详析;评论统一走评论管线(落盘缓存):
     `python3 -m fetch.reviews --platform {ios|play} --ids {逗号分隔 track_id}`
     (工作目录项目根;play 需代理;已落盘自动跳过),读
     `data/{日期}/reviews/{platform}/{track_id}.json`(数组 [{score,text}])
     提炼好评/差评主题。
     - iOS 注意:Apple 评论 RSS 已普遍返回空(端点废弃中)——空文件即
       "该源无评论",标注"评论信息有限,基于描述推断",不要重抓;
       可选 WebFetch `details.track_view_url` 补充页面信息。
     - play 无需抓页面(details 已含 installs/内购/广告)。
6. **智能推荐**:基于本期**可行池**归纳 3-5 个机会品类方向,只从可实现
   赛道中选择(排除清单见下):
   - 四维综合:市场需求(赛道 app 数量/评分——数据文件可得)、竞争蓝海
     (头部集中度,定性)、技术可行性(功能复杂度,定性)、用户痛点
     (deep 有评论时引用评论证据;否则标注"基于描述推断")
   - 每个推荐含:品类方向、机会评级(高/中/低+一句理由)、规模证据
     (只引用数据文件数字)、竞争强度与技术难度(定性+理由)
   - 禁止臆造数值评分(如 8.5/10):定量只用数据文件数字,
     其余标注"AI 定性评估"
7. **写报告**到 `reports/{日期}-工具榜分析-{platform}.md`,结构见下。
   完整榜单表格必须直接写进报告第 4 节(不要只留在中间文件)。
8. 最后向用户输出 3-5 句执行摘要(本期亮点赛道、值得注意的 app、推荐品类)。

## 独立开发者可行性清单

排除原则:按"个人在技术与资源上能否实现"排除,而非"能否竞争过"——
竞争激烈但可实现的赛道留在可行池,由智能推荐按数据评估机会。
调整排除范围时改本清单即可,不改代码。

**不可实现赛道(排除出重点分析、评论抓取与智能推荐):**

| 赛道 | 排除理由 |
|---|---|
| VPN/网络代理(含科学上网类) | 全球服务器集群+持续运维成本 |
| 浏览器 | 引擎级工程量,大厂垄断 |
| 公共服务/政务/数字身份 | 需机构背书与政务数据接入 |
| 运营商/宽带服务 | 运营商专属 |
| 杀毒/防诈/来电识别 | 依赖号码库/病毒样本库等数据基础设施 |
| OEM/智能硬件与车载配套 | 需自有硬件产品或厂商合作生态 |
| 生活服务平台配套(快递物流/房产信息/线下设施) | 需物流网络或双边平台生态 |
| 大厂生态组件(Google/微软配套等) | 平台配套,无独立生态位 |
| 办公套件(全家桶) | Word/WPS 级工程量;单一 PDF/文档工具保留 |
| 远程控制/远程桌面 | 需中继服务器集群 |
| 输入法键盘 | 大厂主导+隐私合规门槛 |
| 云存储/网盘 | 存储基础设施成本 |

**可实现赛道(保留,如):** 清理加速(存储清理/重复照片/通讯录清理)、
密码管理器、单一文档工具(PDF/扫描/格式转换)、文件管理、效率工具、
小组件壁纸、扫描识别、二维码、翻译等其余赛道。

## 重点 app 详析格式(standard/deep 共用)

每个 app 一小节:核心功能(2-4 条中文)/ 目标用户与场景 /
变现模式(免费、买断、订阅、内购或广告——ios 从 `details.price` 与描述推断;
play 直接看 `details.offers_iap`/`iap_price`/`contains_ads` 并引用
`details.installs` 下载量级)/ 一句点评(上榜原因或可借鉴之处)。
`details` 缺失的 app:基于名称与分类推断,并标注"信息有限"。

## 报告结构

1. **本期总览**:日期、平台、区域数、各榜 app 数、数据完整性(skipped)
2. **类型分布**:细分赛道表格(数量/占比/代表 app/独立可行性)+ 共性 vs
   区域特色分析;不可实现赛道行注明排除理由与数量,明确告知本期排除了哪些类型
3. **重点 App 分析**:按细分赛道分组逐个详析(数量按模式)
4. **完整榜单表格**:分区域 × 分榜单,列=排名/名称/开发者/评分/价格(play 加下载量)
5. **观察与机会**:3-6 条跨区域趋势观察与机会点
6. **智能推荐**:基于分析结果推荐最有潜力的3-5个品类方向,只从可实现赛道
   中选择(表述规范见流程第6步)

## 约束

- 全程中文输出;app 名称保留原文(可附中文释义)
- 报告中数字必须来自数据文件,不臆造
- light 模式整份报告控制在 300 行内
- 完整榜单表格保留全量 app(含被排除类别,保证数据完整);排除只作用于
  重点分析、评论抓取与智能推荐

## 智能推荐表述规范

推荐是 AI 综合判断,不是精确算分。数值公式(如加权评分)在
light/standard 模式下没有评论与份额数据支撑,写了只会诱导臆造数字,
故只约定:

- **可定量的**:app 数量、平均评分、评分量、下载量——必须来自
  数据文件并引用
- **定性的**:机会评级、竞争强度、技术难度——用 高/中/低 表述,
  各附一句基于本期数据的理由,并标注"AI 定性评估"
- 输出按报告结构第 6 节列表,不设固定分数格式
